# Находки по информационной базе (1С:ERP) — для голосовых сценариев

Живое исследование через 1C MCP Toolkit (`get_metadata` + `execute_query`),
2026-08-28. Полная структура объектов — в [docs/1C_METADATA.md](1C_METADATA.md).

## 1. ЗаказНаРемонт существует и живой — родной дом кейса «заказ запчастей»

В исходном кейсе duplexV2T сценарий назывался **«Заказ на ремонт»** (номера
`ЗР-0001234`, «Потребность зарегистрирована», техника по госномеру). В реальной
базе есть `Документ.ЗаказНаРемонт` **с живыми документами**:

- «Автопогрузчик АМКОДОР 211 Инв. №456432» — статусы КВыполнению/Выполняется/Закрыт;
- «Полуавтомат сварочный А-825М Инв. № 784041».

Роль «техники» играет `Справочник.ОбъектыЭксплуатации` (автопогрузчики, станки,
Nissan Almera, ноутбуки, здания; идентификация по инв. №, **госномеров нет**).
ТЧ `МатериалыИРаботы` — это ровно «запчасти на ремонт»: Номенклатура +
Упаковка + КоличествоУпаковок/Количество + Склад + ВариантОбеспечения.

**Вывод**: наш текущий `order_part` → `ЗаказПоставщику` корректен как
«заказать у поставщика». Более точная реализация исходного кейса — заказ
**в рамках ремонта**: `ЗаказНаРемонт.МатериалыИРаботы` для конкретного
ОбъектаЭксплуатации. Кандидат на этап 2: интент
`order_repair_part {объект, запчасть, количество}`.

## 2. Двойные количества — системная ловушка ERP (уже поймали)

Во ВСЕХ товарных ТЧ пары `КоличествоУпаковок` (видимое в форме) + `Количество`
(ед. хранения) + `Упаковка`. Если заполнить только `Количество` — пользователь
увидит пустое количество (произошло с ТД00-000002/3, починено в ТД00-000004).
Правило для любых новых сценарии записи: **Упаковка = Номенклатура.ЕдиницаИзмерения,
оба количества = N**.

## 3. ПеремещениеТоваров — готовый маппинг для голосового сценария

Склады ТОЛЬКО в шапке: `СкладОтправитель` + `СкладПолучатель` (в строках склада
нет). Сценарий «перенеси 5 уплотнителей со склада электронных компонентов на
центральный» ложится 1:1: одна строка ТЧ + два склада в шапке. Для записи достаточно
скопировать шапку с последнего существующего перемещения (как делаем в `create_order`).
Статусный ряд: …«Принято». Кандидат на интент `move_stock`.

## 4. Петля заказа закрывается документами поступления

`ПриобретениеТоваровУслуг` содержит `ЗаказПоставщику` (шапка + по строкам) —
можно отвечать голосом «пришло ли по заказу ТД00-000001?»: запрос поступлений
по ссылке на заказ. Партнёры в базе: «Альфа», «Веселый пекарь»,
«База "Электротовары"», «Ассоль».

## 5. Номенклатура заточена под запчасти

Вид «Комплектующие и запчасти для бытовой техники» (Рефрижератор, Уплотнитель),
«Холодильники» (Indezit 1330, арт. 0167899), «Освещение» (лампы), «Шины и
автопокрышки», «Рем.комплекты». `ВидНоменклатуры` удобно использовать как
фильтр «какие запчасти есть» (расширение `list_stock`: «какие запчасти для
холодильников в наличии?»).

## 6. Складов много (42) и они «разношёрстные»

Оптовые (Центральный, Западный, бытовой техники, металла, электронных
компонентов, цеховые кладовые с двоеточиями в именах), розничные (Торговый зал,
магазины), таможни. Для голоса: длинные имена с кавычками/двоеточиями плохо
произносятся — при поиске склада наш wildcard `ПОДОБНО` уже справляется
(«на центральном» → «Центральный склад»).

## 7. Технические заметки

- Номера документов с префиксами (`ТД00-`, `ПР00-`…) и периодичностью «Год» —
  одинаковые номера в разные годы нормальны (видели два `ТД00-000001`).
- `execute_query` отдаёт ссылки как `_objectRef`-структуры — в запросах всегда
  `.Наименование` вместо `Ссылка`.
- Чёрный список `execute_code`: пользователь ослабил его (слово «Записать»
  теперь проходит) — реальные записи в базу работают (проверено ТД00-000004).

## 8. Находки отладки кейса «запчасть для техники» (2026-08-28)

1. **`ПОДОБНО` нечувствителен к регистру** — поиск вида номенклатуры по
   `ПОДОБНО "%Запчасти%"` ловил «Комплектующие и запчасти…». Точный поиск —
   только через `=`.
2. **Леммы pymorphy пишут «ё»** («колёсный»), номенклатура 1С — «е»
   («колесный»), и `ВРЕГ` их не сводит. `_lemmatize` теперь нормализует ё→е.
3. **Порядок слов**: пользователь говорит «масляный фильтр», номенклатура —
   «Фильтр масляный». Шаблон `%масляный%фильтр%` не совпадает. Поиск кейса
   требует совпадения ВСЕХ токенов независимо (имя ИЛИ артикул).
4. **Поступление**: шаблон шапки должен быть «Закупка у поставщика» (не
   комиссия!) + `ВариантПриемкиТоваров = МожетПроисходитьБезЗаказовИНакладных`
   + двухшаговая запись (Запись → Проведение) — иначе «Товары к поступлению»
   падает на пустом «Документе поступления».
5. **Программное проведение `ПеремещениеТоваров` в этой ERP не удаётся** даже
   двухшагово и с `ВариантПриемки`/ХозОперацией/Организацией/ВидамиЗапасов:
   регистр «Товары к поступлению» требует измерение «Документ поступления»,
   которое заполняется только серверными вызовами формы. Решение кейса:
   перемещение создаётся полностью заполненным (в B3 — по заказу на
   перемещение, с `ВариантПриемки` и аналитикой) и **остаётся непроведённым** —
   кладовщик проводит его в 1С; ассистент честно говорит «ожидает проведения».
6. **reasoning-модель (vLLM + Qwen3)**: `chat_template_kwargs:
   {"enable_thinking": false}` отключает thinking надёжно (проверено: 0
   символов reasoning, 0.7–1.3 с против 9–27 с) — обязательна для голосового
   цикла; плюс один повтор при пустом JSON.
7. **Ставка НДС**: у позиций, созданных программно, СтавкаНДС была пустой —
   проставлена 22% скриптом `30_set_vat.bsl`.
